Batch colorization and editing

Plan: select up to 20 JPEG or PNG photos. Run Stable and Tiny on each photo. Edit both results separately, choose one per photo, then save one or all.

Status: version 0.2.3 installers are built locally. A corrected Mac build opened on the target Mac. Windows update and offline use still need testing. The research record is here.

1. Goal and scope

The same German app should handle one photo or a batch. A candidate is one model's colorized result for one photo.

  • Select 1 to 20 JPEG or PNG photos in one native file picker. Reject a larger selection as a whole.
  • Run DeOldify Stable and DDColor Tiny on every selected photo, one photo at a time.
  • Edit each candidate independently. Choose a winner for each photo.
  • Save one chosen result or save all chosen results to one folder.
  • Keep photo bytes on this computer. Clear temporary candidates when the batch closes.
  • Keep the 24-megapixel and 250 MB per-photo limits. Keep the two pinned models and PNG output.
  • Install the new Windows version over the existing app and reuse its downloaded models.
  • Keep large, plain German controls. Put advanced tools behind a closed-by-default section.

No database, cloud upload, Vercel deployment, new model, new image format, photo library, or third-party editing package is in scope.

3. Recommended design

Photo and model queue

  1. The native picker returns photo names and opaque IDs. Main keeps each file path.
  2. Main rejects selections above 20 before reading any full image. It validates file type and the existing byte cap.
  3. The app downloads each missing model once, verifies its size and checksum, and shows progress.
  4. The queue loads one photo, runs Stable, saves its candidate locally, then runs Tiny and saves that candidate.
  5. The queue closes image buffers before starting the next photo. It keeps only one model session active.
  6. If a candidate fails, the app marks it and continues. The user can retry that photo and model later.
  7. Cancel finishes both model runs for the current photo, then stops before the next photo.

If one model download fails, mark that model unavailable for this batch. Continue with the ready model and offer retry after processing.

If one candidate succeeds and the other fails, allow the user to choose the ready candidate. Keep the failed candidate available for retry.

Run inference and large pixel operations in a worker. Keep progress, editing, and Cancel responsive. Finish both attempts for the current photo before stopping.

Handle cancellation during model downloads and failed attempts explicitly. Keep completed candidates and mark unfinished candidates for retry.

The current runtime already holds one model session at a time. This limits memory use on both laptops. It can reload large models often, so the app must show clear progress.

Photo list, comparison, and editor

The batch list shows the original thumbnail, each model's status, and both candidate previews. Selecting a photo opens its full preview and simple controls to switch between Stable and Tiny.

Label Stable ruhiger, empfohlen and Tiny mehr Farbe. Require a separate winner choice for each photo after review.

Each candidate keeps its own edit settings. Show an RGB histogram and these tools in a closed-by-default Weitere Farbeinstellungen section:

  • Keep Farbintensität, Helligkeit, and Wärme.
  • Add Farbton and Tonwertkorrektur for black point, midtones, and white point.
  • Add a master curve and separate Rot, Grün, and Blau curves.
  • Label tools in plain German. Make curve points usable by mouse, touch, and keyboard.

Edits change only the preview and saved copy. They never rerun either model. Reset returns the current candidate to its original output.

Use the same adjustment calculations for the preview and full-resolution export. Preserve image orientation and PNG transparency through colorization and export.

Reuse the current palette and button sizes. Keep the present 20-pixel base text and 58-pixel buttons. Check keyboard use, contrast, and 200% text zoom.

Saving and temporary data

Individual save keeps the current native save dialog and PNG format. The system asks before replacing an existing output. Bulk save opens one folder picker and saves only chosen candidates.

Use <original-name>-farbig.png as the bulk base name. Add -2, -3, and later suffixes when a name exists. Never overwrite a source or saved file during bulk save.

Bulk save includes only photos with a chosen result. Report rows that still need a choice.

Compare each output with every batch original. Account for aliases, case differences, and hard links. Reject any output that could replace an original.

Write each output to a temporary file in the destination folder. Publish it only after the write succeeds. Use exclusive creation for bulk names and handle collisions again at publication.

Report saved, skipped, and failed photos separately. Keep failed candidates available for retry. Clean up only temporary files created by the app.

Main owns the temporary batch directory, selected paths, and output writes. The renderer sees opaque IDs and transfers only one photo or candidate at a time.

Show a confirmation before closing a batch with unsaved work. Remove temporary files on batch close, window close, and app exit. Remove stale app-owned directories on the next launch after a crash.

Keep the current batch until a replacement selection passes validation and the user confirms discarding unsaved work.

Windows update

Increase the app version and build an unsigned Windows x64 installer that updates the existing installation. Preserve the app ID, product name, install scope, and user-data location.

Keep both cached model files during installation and updates. Check their existing sizes and checksums before reuse. Download a model only if its cache is missing or invalid.

Close the app before installing the update. Reopen it afterward and process photos offline with both cached models.

6. Acceptance and checks

  • Selecting 20 valid photos succeeds. Selecting 21 rejects the whole selection and leaves the open batch intact.
  • Each valid photo receives both model runs. A failed photo or model candidate does not stop later work.
  • Cancel completes the current photo's Stable and Tiny attempts. It starts no next photo and keeps all completed files.
  • Progress and Cancel stay responsive during inference, pixel processing, and model downloads.
  • Retry reruns only the failed photo and model candidate. It does not rerun successful candidates.
  • Each candidate retains its own settings. Neutral settings reproduce its model output. Edits do not rerun inference.
  • Hue, levels, channel curves, histogram labels, reset, and keyboard curve controls work on the maximum allowed image size.
  • Users can choose a winner for each photo. Individual and bulk saves create PNGs and leave source files unchanged.
  • Bulk save includes only selected winners and reports photos without a winner.
  • Bulk save asks for one folder, uses unique names, and reports every saved or failed file.
  • Saving cannot replace any batch original through aliases, hard links, or case differences. Interrupted writes never appear as completed PNGs.
  • Preview and full-resolution export use the same adjustments. Neutral output, orientation, and PNG transparency remain correct.
  • Invalid replacement selections leave the open batch intact. Closing unsaved work requires confirmation.
  • Closing the batch removes only app-owned temporary files. Startup removes only stale directories under its own temporary root.
  • No photo data or path is sent to a network. Both cached models work offline.
  • Install the new Windows package over the previous version with both models cached. Compare their sizes and checksums before and after the update. Confirm no model download occurs.
  • After updating, disconnect the Windows laptop from the internet. Run both models on a photo and save a result.
  • With one missing or invalid cached model, download only that model and verify its size and checksum before use.

7. Risks, safeguards, and rollback

  • Stable took over 30 seconds for one portrait in the prior app check. Two models across 20 photos can take a long time. Show the current photo and model at all times.
  • Temporary results need disk space. If a write fails, mark that candidate, keep completed results, and continue with other candidates.
  • Available disk space can change during a run. Handle full disks and interrupted writes without losing completed results or replacing existing files.
  • The Windows laptop's RAM and runtime speed are unknown. Keep one model session active and record device validation separately.
  • Keep the existing context isolation, sandbox, CSP, IPC sender checks, PNG signature checks, 24-megapixel cap, and original-file protection.
  • Do not include photo bytes, file paths, or family-photo names in logs. Do not add network calls for photos.

No database migration is needed. To roll back a committed feature, review its exact commit and run git revert <feature-commit-hash>. Keep generated installers outside Git.
